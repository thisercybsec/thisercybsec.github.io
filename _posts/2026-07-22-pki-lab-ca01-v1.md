## Role

Offline Root CA. The top of the trust chain — signs exactly one thing
(CA02's subordinate certificate) and then stays powered off for the rest
of its life. Deliberately **not domain-joined**, so the Root CA's private
key has zero AD dependency and zero network attack surface once it's
shut down.

**Static config:** `192.168.10.2` / `255.255.255.0`, DNS left blank
(doesn't need to resolve `lab.local` since it never talks to the domain).

## Build Steps

1. VM renamed to `CA01` in both VirtualBox settings and Windows hostname.
2. Static IP set: `192.168.10.2` / `255.255.255.0`, DNS blank.
3. Kept as a standalone workgroup machine — **not** joined to the domain.
4. Installed AD CS role — **Certification Authority** role service only
   (no Web Enrollment needed on an offline root).
5. Configured as:
   - Setup Type: **Standalone CA**
   - CA Type: **Root CA**
   - New private key, **4096-bit**, **SHA256**
   - CA Name: `Lab Root CA`
   - Validity: **10 years**

### CDP/AIA configuration

Critical step, done *before* taking CA01 offline for good — since CA01
won't be reachable most of the time, any certificate it signs needs its
CDP/AIA extensions pointing somewhere that stays reachable (CA02's
web-served CertEnroll folder), not back at CA01 itself.

```powershell
certutil -setreg CA\CRLPublicationURLs "1:C:\Windows\system32\CertSrv\CertEnroll\%3%8%9.crl\n2:http://ca02.lab.local/CertEnroll/%3%8%9.crl"
certutil -setreg CA\CACertPublicationURLs "1:C:\Windows\system32\CertSrv\CertEnroll\%1_%3%4.crt\n2:http://ca02.lab.local/CertEnroll/%1_%3%4.crt"
certutil -setreg CA\CRLPeriodUnits 26
certutil -setreg CA\CRLPeriod "Weeks"
certutil -setreg CA\CRLDeltaPeriodUnits 0
net stop certsvc
net start certsvc
certutil -crl
```

Delta CRLs disabled and the base CRL period extended to 26 weeks, since
an offline root can't reliably publish on a short interval — it's not
even powered on most of the time.

6. Exported the Root CA certificate: Certification Authority console →
   right-click CA → Properties → View Certificate → Details → Copy to
   File → **Base-64 encoded X.509 (.CER)** → saved and later renamed
   using a `CA01_Lab Root CA` filename convention.

## Troubleshooting

**Booted into an iPXE network boot prompt instead of Windows**, right
after attempting to install Guest Additions. Cause: VirtualBox Settings
→ System → Motherboard had **Network** checked/prioritized in the boot
order. Fix: powered off, unchecked Network, confirmed Hard Disk was
checked and prioritized, booted normally.

**Guest Additions install:** used `VBoxWindowsAdditions-amd64.exe`
directly (not the generic auto-detect launcher) for reliability on
Server 2022, then enabled Bidirectional Shared Clipboard via the Devices
menu afterward.

## Handoff to CA02

File transfer between CA01 and CA02 uses a VirtualBox **Shared Folder**
(`C:\LabTransfer` on the host, mounted as `\\VBOXSVR\LabTransfer`) rather
than networking the two CA boxes directly — this preserves CA01's
offline/air-gapped status, since shared folders route through the
hypervisor rather than the internal virtual network.
