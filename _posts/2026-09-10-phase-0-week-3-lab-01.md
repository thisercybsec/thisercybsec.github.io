## Objective

Deploy the Cowrie SSH honeypot two ways on the same isolated honeypot VLAN (`10.10.20.0/24`) — once as a bare-metal install and once as a Docker container — and compare the setup process, configuration, and resulting captured sessions side by side.

## Environment

- Host: `testbox3`, Ubuntu 26.04.1 LTS (minimized install), kernel `7.0.0-31-generic`
- Network: VLAN 20 (honeypot segment) behind pfSense
- Bare-metal SSH port: `2222`
- Docker SSH port: `2223` (Telnet remapped to `2323` to avoid a collision with the SSH port)

## Prerequisite setup

Before touching Cowrie itself, the host needed:

- `sudo apt update && sudo apt upgrade -y`
- Build dependencies: `libssl-dev`, `libffi-dev`, `build-essential` — required for compiling `cryptography` and other Python packages during `pip install`
- A dedicated, low-privilege `cowrie` user (`sudo adduser --disabled-password cowrie`) so the honeypot process never runs as root
- Verified Python/venv worked under that user, and confirmed outbound connectivity (`git ls-remote`) before attempting a real clone

**Gotcha:** mid-dependency-install, `apt` appeared to hang at 99% on `libc-bin`'s triggers. The console later revealed a genuine kernel soft lockup (`watchdog: BUG: soft lockup - CPU#0 stuck for 1705s!`), most likely from CPU scheduling contention on the VirtualBox host rather than anything wrong with the package install itself. Sending an ACPI shutdown signal snapped the stuck process loose; a reboot afterward cleared a pending kernel upgrade (`7.0.0-30-generic` → `7.0.0-31-generic`) and came back clean with no repeat lockup. Lesson: after any forced interrupt of `apt`/`dpkg`, run `sudo dpkg --configure -a` and `sudo apt --fix-broken install` before trusting the package state.

## Bare-metal install

```
git clone https://github.com/cowrie/cowrie
cd cowrie
python3 -m venv cowrie-env
source cowrie-env/bin/activate
python -m pip install --upgrade pip
python -m pip install --upgrade -r requirements.txt
```

All dependencies installed cleanly under **Python 3.14.4** — including `cryptography` and `twisted`, both of which shipped prebuilt `cp314` wheels. The Python 3.14 compatibility concern flagged going in turned out to be a non-issue.

**Gotcha — repo layout:** this version of Cowrie has moved to a `src/`-layout Python package. There is no `bin/cowrie` launcher and no pre-populated `etc/` directory as older tutorials assume. The actual template configs live at `src/cowrie/data/etc/`:

```
cp src/cowrie/data/etc/cowrie.cfg.dist etc/cowrie.cfg
cp src/cowrie/data/etc/userdb.example etc/userdb.txt
pip install -e .
```

`pip install -e .` builds the package from `pyproject.toml` and creates a real `cowrie` executable inside the venv's own `bin/` (`cowrie-env/bin/cowrie`), which is what actually needs to be run — not a repo-root `bin/cowrie` script.

Configuration: `listen_endpoints = tcp:2222:interface=0.0.0.0` was already correct out of the box; `hostname` was changed to `TestServer` for this test run. Telnet stayed disabled (default).

```
cowrie start
```

Confirmed via `cowrie status`, the log (`Ready to accept SSH connections`), and `ss -tlnp | grep 2222`.

## Docker install

Docker wasn't yet installed on the host. Installed via Docker's official APT repository (not Ubuntu's bundled `docker.io`) for current Engine/Compose/Buildx builds:

```
sudo apt install apt-transport-https ca-certificates curl -y
sudo install -m 0755 -d /etc/apt/keyrings
sudo curl -fsSL https://download.docker.com/linux/ubuntu/gpg -o /etc/apt/keyrings/docker.asc
sudo chmod a+r /etc/apt/keyrings/docker.asc
echo "deb [arch=$(dpkg --print-architecture) signed-by=/etc/apt/keyrings/docker.asc] https://download.docker.com/linux/ubuntu $(. /etc/os-release && echo "$VERSION_CODENAME") stable" | sudo tee /etc/apt/sources.list.d/docker.list > /dev/null
sudo apt update
sudo apt install docker-ce docker-ce-cli containerd.io docker-buildx-plugin docker-compose-plugin -y
```

Docker's repo already had full support for Ubuntu 26.04's `resolute` codename — no fallback needed. Verified with `sudo docker run hello-world`.

**Gotcha:** the install stalled partway through with zero CPU and zero disk activity for several minutes, and neither the console nor Ctrl+C responded — likely a stalled network read that also happened to coincide with a keyboard-capture issue in the VirtualBox console. Resolved with a VM restart, followed by `sudo dpkg --configure -a` before retrying the install cleanly.

The cloned Cowrie repo ships its own `docker/Dockerfile` and `docker/docker-compose.yml`, so the container was built from the same source tree already used for the bare-metal install rather than pulling a separate image from Docker Hub. The default compose file maps host port **2222** for SSH and **2223** for Telnet — both of which collided with the existing plan, so both were overridden:

```
sudo COWRIE_SSH_PORT=2223 COWRIE_TELNET_PORT=2323 docker compose \
  -f /home/cowrie/cowrie/docker/docker-compose.yml up -d --build
```

Build took roughly 10 minutes, most of it in the dependency-install layer (equivalent to the bare-metal `pip install` step, but without any cached downloads to reuse). Verified via `docker ps`, `docker logs docker-cowrie-1`, and `ss -tlnp | grep 2223`.

The compose file also applies real container hardening out of the box: `cap_drop: [ALL]`, `read_only: true`, `security_opt: [no-new-privileges:true]` — a meaningfully different isolation model than the bare-metal deployment's plain unprivileged-user approach.

## Captured sessions — comparison

Both deployments were tested with `ssh -p <port> root@127.0.0.1`, logging in with a non-`"root"` password (Cowrie's default `userdb.txt` rule rejects the literal string `"root"` but accepts most other passwords for that username) and running the same handful of recon-style commands (`ls`, `cd`, `whoami`, `uname -a`) before exiting.

| | Bare-metal (2222) | Docker (2223) |
|---|---|---|
| Python version | 3.14.4 | 3.13.5 |
| Logged source IP | `127.0.0.1` (direct) | `172.18.0.1` (Docker bridge NAT) |
| SSH warnings | none | `No moduli, no diffie-hellman-group-exchange-sha1/sha256` |
| Isolation model | dedicated unprivileged `cowrie` user | `cap_drop: ALL`, read-only rootfs, no-new-privileges |
| Session outcome | Full session captured, exit code 0, TTY log saved | Full session captured, exit code 1, TTY log saved |

Two differences stood out as directly attributable to the deployment method rather than configuration:

- **Source IP handling.** The bare-metal instance logged the real connecting address directly. The Docker instance logged the address of Docker's own bridge gateway (`172.18.0.1`) instead of the true client address, because Docker's default bridge network NATs inbound connections before they reach the container. This is a real operational difference worth accounting for if this were ever deployed for actual traffic analysis — the Docker deployment would need `--network host` or a custom bridge on the honeypot VLAN itself to preserve real source IPs, at the cost of losing some of the container's network isolation.
- **Missing SSH moduli.** The Docker image doesn't ship a moduli file for the older `diffie-hellman-group-exchange-sha1`/`sha256` key exchange algorithms, logged as warnings on connection. It didn't break anything — the session still completed cleanly — but it's a small authenticity gap that could be a fingerprinting signal for a sufficiently careful attacker (or scanner) probing the honeypot's supported KEX algorithms.

## Conclusion

Both deployment paths reached the same end state — a working Cowrie honeypot with a fully captured, logged SSH session — but got there differently enough to be worth documenting. The Docker path front-loaded more setup friction (installing Docker itself, working around the compose file's default port collisions, a materially longer build) but delivered stronger process isolation by default and a self-contained, reproducible environment independent of the host's Python version. The bare-metal path was faster to stand up once dependencies were in place, but ties the honeypot's Python environment directly to whatever the host happens to be running — which, in this case, meant landing on a very new Python release (3.14.4) sooner than might otherwise have been chosen deliberately.

Most of this session's actual time went into environment troubleshooting unrelated to Cowrie itself — a kernel soft lockup during `apt`, a stalled Docker install, and repeated VirtualBox console keyboard-capture issues — a good reminder that homelab work spends as much time on infrastructure friction as on the tool being deployed.
