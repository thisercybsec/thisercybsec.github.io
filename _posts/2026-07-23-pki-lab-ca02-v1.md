## Role

The online Enterprise Issuing/Subordinate CA — the box that actually
does the day-to-day work of signing certificates once the hierarchy is
live. Domain-joined, since Enterprise CA setup and certificate
autoenrollment both depend on Active Directory.

**Static config:** `192.168.10.3` / `255.255.255.0`, DNS `192.168.10.1`
(points at DC01 — required for the domain join to succeed).

## Build Steps

1. VM renamed to `CA02`.
2. Static IP set: `192.168.10.3` / `255.255.255.0`, DNS `192.168.10.1`.
3. Joined to `lab.local` using `LAB\Administrator` credentials.
4. Logged back in post-restart as `LAB\Administrator` (a domain account
   is required for Enterprise CA setup).
5. Installed AD CS role with **both** role services: Certification
   Authority + Certification Authority Web Enrollment (which pulls in
   IIS as a dependency).
6. Configured as:
   - Setup Type: **Enterprise CA**
   - CA Type: **Subordinate CA**
   - New private key, **2048-bit**, **SHA256**
   - CA Name: `Lab Issuing CA` (displays in console as `Lab-Issuing-CA`)
   - Certificate Request: **saved to file** — there's no live parent CA
     to submit to directly since CA01 stays offline — producing a
     `.req` file.

### Getting the request signed by CA01

7. Transferred the `.req` file to CA01 via the VirtualBox shared folder
   (`\\VBOXSVR\LabTransfer`) — see [CA01's post]({% post_url 2026-07-22-pki-lab-ca01-v1 %})
   for why a shared folder instead of direct networking.
8. On CA01: submitted the request via Certification Authority console →
   All Tasks → Submit new request → located it in **Pending Requests** →
   issued it via All Tasks → Issue → moved to Issued Certificates →
   exported as Base-64 `.cer`.
9. Copied the issued Subordinate cert *and* the Root CA cert + CRL back
   to CA02 via the same shared folder.

### Installing the chain on CA02

10. Imported the Root CA cert into **Trusted Root Certification
    Authorities** (`mmc` → Certificates snap-in → Computer account →
    Local computer).
11. Installed the signed Subordinate cert onto the CA: Certification
    Authority console → All Tasks → **Install CA Certificate** →
    selected the `.cer` file.
12. Copied the Root CA's `.crl` and cert files into CA02's own
    `C:\Windows\System32\CertSrv\CertEnroll\` folder, to satisfy the
    CDP/AIA paths configured back on CA01.
13. Started Certificate Services (All Tasks → Start Service) —
    operational.

## Troubleshooting

**Domain join failed:** *"An Active Directory Domain Controller (AD DC)
for the domain 'lab.local' could not be contacted."* Resolved by
systematically checking each layer: DC01 powered on → LABNET adapter
naming matched exactly between VMs → static IP/DNS config confirmed via
`ipconfig /all` → `ping 192.168.10.1` and `nslookup lab.local` used to
isolate a network-layer failure from a DNS-layer one.

```powershell
ipconfig /all
ping 192.168.10.1
nslookup lab.local
```

**Certificate Import Wizard confusion:** right-clicking the top-level
"Certificates (Local Computer)" node in `mmc` only exposes Find/Connect/
Auto-enroll — no Import option there. Had to expand two levels deeper
into **Trusted Root Certification Authorities → Certificates** (the
nested subfolder) before Import became available via right-click → All
Tasks.

**"Install CA Certificate" file dialog showed no files:** the default
file-type filter was set to PKCS #7 (`*.p7b`), which hid the `.cer` file
entirely. Switched the filter to X.509 Certificate (`*.cer`) to reveal it.

**Service failed to start with a revocation error:**

```
0x80092013 (-2146885613 CRYPT_E_REVOCATION_OFFLINE)
"The revocation function was unable to check revocation because the
revocation server was offline."
```

Root cause: the Root CA's `.crl` file had never actually been copied
into CA02's `CertEnroll` folder — only the certificate files had made
the trip, not the CRL itself. Fixed by retrieving `Lab Root CA.crl` from
CA01's `CertEnroll` folder via the shared transfer folder and placing it
in the equivalent path on CA02. Service started cleanly immediately
after.

This turned out to be the single most useful debugging lesson from the
whole build: **a valid trust chain can still fail to start if the CRL
file itself isn't physically sitting where the CDP/AIA extension says it
should be** — the chain being "trusted" and the file actually being
present at that path are two separate things to verify.
