## The rabbit holes (honest accounting)

Three of the six containers didn't come up clean on the first try. Each turned out to trace back to a version of the same underlying problem: T-Pot maintainer images (`dtagdevsec/*`) sometimes ship configs or entrypoint scripts that assume a directory tree the image itself doesn't actually contain.

### OpenCanary: stale pidfile after an OOM kill

OpenCanary had been sitting `Exited (137)` — a SIGKILL, most likely OOM — for several days without my noticing. Restarting it produced a clean `Exited (1)` instead, with a twisted/twistd log message: *"Another twisted server is running... use `--pidfile`/`--logfile` to avoid clashes."*

The 137 kill never let the app clean up its own pidfile, so every restart found the stale file and refused to start, even though nothing else was actually running. Since `docker inspect --format '{{json .Mounts}}'` showed only a bind-mounted config file and no persistent data volume, the stale pidfile lived entirely in the dead container's throwaway filesystem. Fix: `docker rm` + recreate with the same `Cmd`, port bindings, and mount (captured via `docker inspect` before removing).

### Dionaea: config pointed at a directory that doesn't exist

Dionaea started fine but produced no logs and threw several `critical` startup errors: `The basedir '/opt/dionaea/var/dionaea/roots/ftp' is not a directory`, and similar for `binaries/`.

Root cause: `dionaea.cfg` and three service YAMLs (`http.yaml`, `tftp.yaml`, `ftp.yaml`) all reference a `/opt/dionaea/var/dionaea/` log/data tree that simply isn't present in the shipped image — the actual layout is `/opt/dionaea/var/{lib,log}/`. Default logging was also commented out in the config (`#default.filename=...`).

Fix:
1. Uncommented the `default.*` logging lines in `dionaea.cfg`.
2. `sed`'d every `var/dionaea/` reference to `var/log/` across the main config and all three service YAMLs.
3. `mkdir -p` + `chown dionaea:dionaea` the missing subdirectories (`roots/{www,tftp,ftp}`, `binaries/`) — sed only rewrites text, it doesn't create directories.

Note for later: Dionaea logs to a file (`/opt/dionaea/var/log/dionaea.log`), not stdout, so `docker logs` shows nothing for it even when it's completely healthy — worth remembering before assuming a silent `docker logs` means something's wrong.

### Redis honeypot: bind-mount ownership mismatch

`dtagdevsec/redishoneypot` exited immediately with `sh: can't create /var/log/redishoneypot/redishoneypot.log: nonexistent directory`. Same underlying problem as Dionaea — bind-mounted a host directory at that path to fix it.

That produced a second failure: `Permission denied` on the same file. The container runs as UID/GID `2000:2000` internally (confirmed via `docker inspect --format '{{.Config.User}}'`), and a bind mount checks UID numbers, not usernames — the host directory was owned by my own host user, not `2000:2000`. `chown -R 2000:2000` on the host-side mount directory resolved it.

## Docker commands used

The commands that came up repeatedly enough to be worth keeping as a reference:

```bash
# container lifecycle
docker ps -a --format "table {{.Names}}\t{{.Status}}"
docker start <name>
docker restart <name>
docker rm <name>
docker stats --no-stream

# inspecting a container
docker inspect <name> --format '{{json .Mounts}}'
docker inspect <name> --format '{{.Config.Cmd}}'
docker inspect <name> --format '{{.Config.User}}'
docker inspect <name> --format '{{json .HostConfig.PortBindings}}'

# editing config inside a container (as root, since exec defaults to the container's app user)
docker exec -it -u root <name> sed -i 's|old/path|new/path|g' <file>
docker exec -it -u root <name> mkdir -p <path>
docker exec -it -u root <name> chown -R <user>:<group> <path>
```

## Takeaways

- Idle resource footprint isn't the bottleneck for a multi-honeypot host — configuration correctness is. Every failure this lab was a shipped-image config assuming a directory structure that didn't exist, not a resource or networking problem.
- `docker logs` being empty doesn't mean a container is unhealthy — check whether the app logs to stdout at all before assuming something's broken.
- A crashed container's leftover pidfile can masquerade as "another instance is running" indefinitely; checking for a persistent volume first tells you whether `docker rm` + recreate is a safe fix.
