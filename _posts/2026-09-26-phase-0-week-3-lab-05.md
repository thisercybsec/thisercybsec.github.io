## Objective

Deliberately "compromise" a Docker-based honeypot, time how long it takes to detect, then compare recovery speed via a `docker compose down`/`up` rebuild. This drill is a dry run for the "fast rebuild after compromise" design goal queued for Phase 2.

## Setup

Before running the drill, I needed basic visibility into the container stack, since nothing was being monitored yet. Set up a three-pane `tmux` session on testbox3:

- **Pane 1:** `watch -n 2 docker ps` — live container status
- **Pane 2:** `docker logs -f docker-cowrie-1` — live Cowrie log stream
- **Pane 3:** free pane for running commands

Target container: `docker-cowrie-1` (Cowrie SSH honeypot, chosen over the other five honeypots on this host since it's the most active/interactive and gives the clearest signal for "when did I notice").

## Attempt 1: `docker exec` (failed)

First attempt was to plant a marker file inside the container via `docker exec`:

```
docker exec docker-cowrie-1 sh -c 'touch /tmp/pwned && echo "compromised $(date)" > /tmp/pwned'
```

This failed immediately:

```
OCI runtime exec failed: exec failed: unable to start container process: exec: "sh": executable file not found in $PATH
```

Tried `/bin/sh` explicitly, then `ls`, `touch`, and `which` directly — all failed the same way. Turns out this Cowrie image ships with **no shell and no coreutils at all**. `docker exec` can't run anything inside it, since there's nothing on `$PATH` to run. This is a deliberate minimal-image hardening choice — smaller attack surface, but it also means you can't just shell in to poke at it.

## Attempt 2: `docker cp` (failed)

Next tried copying a file in directly, bypassing the need for a shell:

```
echo "compromised $(date)" > pwned.txt
docker cp pwned.txt docker-cowrie-1:/tmp/pwned
```

`docker cp` reported success, but the file didn't actually land:

```
Error response from daemon: container rootfs is marked read-only
```

The container's root filesystem is mounted **read-only** — another hardening measure. So `/tmp` inside the container isn't writable at all unless it's a path backed by a separate mount.

## Attempt 3: writing directly to the volume mount (success)

Checked the container's mounts:

```
docker inspect docker-cowrie-1 --format '{{range .Mounts}}{{.Destination}} -> {{.Source}}{{"\n"}}{{end}}'
```

```
/cowrie/cowrie-git/etc -> /var/lib/docker/volumes/docker_cowrie-etc/_data
/cowrie/cowrie-git/var -> /var/lib/docker/volumes/docker_cowrie-var/_data
```

`/cowrie/cowrie-git/var` (Cowrie's runtime/log data directory) is backed by a named volume, and named volumes are writable from the host side regardless of the container's read-only rootfs. Resolved the actual host mountpoint:

```
docker volume inspect docker_cowrie-var --format '{{.Mountpoint}}'
```

Wrote the marker directly to that host path:

```
sudo sh -c 'echo "compromised $(date)" > /var/lib/docker/volumes/docker_cowrie-var/_data/pwned'
```

(First attempt at this had a typo — `columes` instead of `volumes` — which produced a "directory nonexistent" error that initially looked like a real path problem. Worth double-checking the literal path before assuming the volume itself is misconfigured.)

Verified:

```
sudo cat /var/lib/docker/volumes/docker_cowrie-var/_data/pwned
compromised Sun Sep 27 00:41:47 UTC 2026
```

## Detection check

With the marker planted, checked both monitoring panes: **nothing changed.** No new entries in `docker logs -f docker-cowrie-1`, no status change in `docker ps`. This makes sense in hindsight — writing a file into the volume backing Cowrie's data directory isn't an SSH-session event, so Cowrie has no reason to log it, and `docker ps` only reports container-level state, not filesystem contents.

**Finding:** a file dropped straight into a bind-mounted/volume-backed path is invisible to both container-level status checks and the honeypot's own application logs. Catching this would require host-level file integrity monitoring (e.g. AIDE, or Wazuh's FIM module) — which is exactly the kind of gap the Phase 4/5 monitoring stack is meant to close.

## Rebuild timing

`docker-compose` (the standalone hyphenated binary) wasn't installed on this host — only the newer built-in `docker compose` (v2, space-separated) subcommand:

```
docker compose version
Docker Compose version v5.5.1
```

Also hit a permissions wall trying to `cd` into the directory containing the compose file (`/home/cowrie/cowrie/docker/`, owned by the `cowrie` user) — `sudo cd` doesn't work since `cd` is a shell builtin, not an executable `sudo` can run. Worked around it with `-f` to point at the compose file directly instead of `cd`-ing in:

```
sudo docker compose -f /home/cowrie/cowrie/docker/docker-compose.yml down cowrie
sudo docker compose -f /home/cowrie/cowrie/docker/docker-compose.yml up -d cowrie
```

Compose reported timing directly:

```
[+] down 2/2
 - Container docker-cowrie-1  Removed     0.3s
 - Network docker_default     Removed     0.1s

[+] up 2/2
 - Network docker_default     Created     0.1s
 - Container docker-cowrie-1  Started     0.4s
```

**Total rebuild time: ~0.9 seconds** (0.4s down, 0.5s up).

## Persistence check

Re-checked the marker after the rebuild:

```
sudo cat /var/lib/docker/volumes/docker_cowrie-var/_data/pwned
compromised Sun Sep 27 00:41:47 UTC 2026
```

**Still there.** The container itself was genuinely torn down and recreated (Compose's `Removed`/`Created`/`Started` output confirms this — it wasn't a no-op), but `docker compose down` without `-v` only removes containers and networks by design — named volumes are meant to persist across redeploys so you don't lose legitimate data like logs and config on every restart.

**Finding:** a routine rebuild does *not* guarantee a clean slate if a compromise touched a persistent volume. `down -v` would clear it, but that also wipes legitimate data sharing the same volume (Cowrie's real session logs, config) — there's no way to selectively purge just attacker-planted files without splitting attacker-writable paths from "keep forever" data into separate volumes. Worth designing for later, once I'm structuring volumes for the actual AWS deployment.

## Results summary

| Metric | Result |
| --- | --- |
| Detection (via `docker ps`/logs) | Not detected |
| Rebuild time (`down` + `up`) | ~0.9s |
| Marker survives rebuild? | Yes — volume persists across `down`/`up` |

## Takeaways

- Minimal/hardened container images (no shell, read-only rootfs) resist casual poking but also block straightforward `exec`-based testing — writing to volume mounts from the host side is the workaround.
- Container-level monitoring (`docker ps`, `docker logs`) has a real blind spot for filesystem-level tampering that doesn't generate an application log event — host-level FIM is a genuine gap right now, not just theoretical.
- Fast container rebuilds (sub-second) don't equal a clean recovery on their own — volume persistence needs to be part of the incident-response plan, not just container lifecycle.
