## Objective

Before deciding how the honeynet itself will eventually be exposed to the internet, I wanted to actually *see* the difference between a host sitting behind pfSense's NAT and a host bridged directly onto the LAN with no firewall in front of it. This lab compares both cases at the packet level using `tcpdump` and `nmap`, previewing the exact exposure-mode decision that will get formalized later when the honeypot goes live.

## Topology

- **Host machine (Windows)** — `192.168.1.50` on the home LAN, Wi-Fi adapter. Plays the role of an external attacker scanning in.
- **pfSense WAN** — Bridged Adapter, `192.168.1.10` on the same home LAN segment. This is the NAT boundary under test.
- **Test VM A — Ubuntu ("NAT'd")** — Honeypot VLAN, `10.10.20.10/24`, reaches the internet via pfSense outbound NAT. No port-forward rule exists pointing at it.
- **Test VM B — AlmaLinux ("bridged/exposed")** — Bridged Adapter straight to the host's physical NIC, `192.168.1.30/24`. No firewall in front of it at all.

## Method

1. Confirmed both test VMs had working internet access (`ping -c 4 8.8.8.8` on each) before touching anything else.
2. Installed Nmap + Npcap on the Windows host to serve as the scanner.
3. Ran `tcpdump` on the relevant capture point for each target:
   - pfSense WAN interface (`em0`) for the NAT'd case
   - Alma's own interface (`enp0s3`) for the bridged case, since there's no firewall hop to sit in front of
4. Ran a scan from Windows against each target's IP and compared what showed up in the capture.

## Bugs & Debugging (documented honestly)

This lab had more troubleshooting in it than actual scanning, which is on-brand for how this project gets documented.

**1. `tcpdump` filtered on the wrong host initially.**
First capture attempt filtered on `192.168.1.1` — that's the home router, not the Windows scanner. Result was a screen full of irrelevant ARP/IGMP chatter with none of the actual scan traffic. Fixed by re-filtering on the scanner's real IP (`192.168.1.50`).

**2. Typo'd the Nmap flag.**
Tried `-Ss` instead of `-sS` — invalid flag, Nmap rejects it outright. Correct SYN scan flag is lowercase `s`, capital `S`.

**3. `tcpdump` syntax error from a dropped `-i`.**
On Alma, ran `sudo tcpdump enp0s3 -n host 192.168.1.50` without the `-i` flag — tcpdump tried to parse the interface name as part of the filter expression and threw a syntax error. Fixed by adding `-i` before the interface name.

**4. SYN scan (`-sS`) silently failed over Wi-Fi.**
Even with Npcap correctly installed (confirmed via `nmap --version` showing `Npcap-0.9982` in the compiled feature list) and ARP resolving cleanly (`arp -a` showed a valid dynamic entry for the pfSense WAN IP), the `-sS` scan against pfSense returned "0 hosts up" in ~1.5 seconds — too fast to be a real result, and the pfSense-side tcpdump showed **nothing arriving at all**. Root cause: raw packet injection over a Wi-Fi adapter is unreliable on Windows because Npcap has to translate between 802.11 framing and the Ethernet framing Nmap expects for hand-crafted SYN packets, and that translation layer doesn't always work depending on the Wi-Fi driver. This is a known, documented gotcha and not something misconfigured on my end. Switched to `-sT` (TCP connect scan, using the OS's real TCP stack instead of raw packets) as the workaround, which worked over Wi-Fi without issue.

**5. The pfSense `-sT` scan "never finished."**
This one turned out to be the actual finding, not a bug — see Results below.

## Results

### Alma (bridged, no firewall)

`nmap -sT -Pn 192.168.1.30` completed in a couple of seconds. Filtering the capture for SYN-ACK responses:

```
tcpdump -r alma_scan.pcap -n 'tcp[tcpflags] & (tcp-syn|tcp-ack) == (tcp-syn|tcp-ack)'
```

showed real open ports answering directly:

- **22/tcp (ssh)** — open
- **9090/tcp (websm)** — open

Every scanned port got an immediate, honest answer — either a SYN-ACK (open) or presumably an RST for closed ports. Alma has zero filtering between it and anyone on the LAN; if this were a real public IP instead of a home network address, this is exactly what an internet-facing attacker would see on first scan.

### pfSense WAN (NAT'd, no port-forward)

`nmap -sT -Pn 192.168.1.10` never completed in a reasonable timeframe. The pfSense-side capture showed the same SYN packet being retransmitted repeatedly against many destination ports, with **zero replies of any kind** — no RST, no SYN-ACK, nothing:

```
18:26:15.962959 IP 192.168.1.50.16076 > 192.168.1.10.63331: Flags [S], ...
18:26:15.965673 IP 192.168.1.50.16077 > 192.168.1.10.49176: Flags [S], ...
...
```

Because a TCP connect scan relies on the OS to wait out a full connection timeout per port when nothing comes back, silent-drop behavior turns what should be a fast scan into one that effectively never finishes. This was cancelled early (`Ctrl+C`) rather than waited out, since the behavioral evidence was already conclusive.

A separate, isolated ICMP test earlier in the lab confirmed the same pattern: four echo requests sent to pfSense's WAN IP, ARP resolved successfully (`192.168.1.10 is-at 08:00:27:aa:bb:cc`), but zero ICMP replies — again, silent drop rather than rejection.

## Key Takeaway

**NAT without an explicit port-forward behaves as implicit default-deny — but by silent drop, not rejection.** This has a real, observable side effect beyond just "the attacker sees nothing": scans against a silently-dropping target take dramatically longer than scans against a host that answers honestly, because the scanning tool has to time out on every single probe instead of getting a fast RST or SYN-ACK back. A bridged host with no firewall, by contrast, answers instantly and honestly on a per-port basis — which is fast for a scanner, but it means everything actually running on that box is immediately visible to anyone on the network.

This is the exact tradeoff I'll need to reason about when picking the honeypot's exposure mode later on: a honeypot needs to look *believably reachable* to attract scans and interaction, but the containment layer still needs to control what happens after that initial contact — this lab is the first hands-on look at where that line actually sits at the packet level.
